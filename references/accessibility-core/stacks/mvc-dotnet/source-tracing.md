# Source tracing — from a live DOM node back to the Razor / .NET / script source

> **OPTIONAL REFERENCE — browser skill only, read on demand.**
> ASP.NET MVC / Razor surfaces only. The principles shared with every stack (fix the generator, choosing
> the ladder in a Hybrid repo, confirming a fix reached the DOM) live in `../../common/source-tracing.md`.

In a Razor app a DOM node was produced by one of: a **view**, the **layout**, a **partial**, an
**Editor/Display template**, a **View Component**, a **Tag Helper**, an **HTML Helper**, **JavaScript/jQuery**
that ran after load, an **AJAX response** that replaced part of the page, or a **third-party widget**. The fix
goes in a different place for each. There is no framework debug API that names the owner, so the ladder
relies on evidence. Stop at the first rung that gives an unambiguous answer.

---

## Rung 1 — Server-rendered or script-generated?

The single most decisive question. Compare the live node with the HTML the server actually sent:

```js
// Safe only for a page reached by GET. Never re-request a POST result page.
const sel = '<the failing selector from axe>';
const live = document.querySelector(sel);
const served = await fetch(location.href, { credentials: 'same-origin' }).then(r => r.text());
const doc = new DOMParser().parseFromString(served, 'text/html');
const srv = doc.querySelector(sel);
({ inServerHtml: !!srv,
   serverAttrs: srv ? [...srv.attributes].map(a => a.name + '=' + a.value.slice(0, 40)) : null,
   liveAttrs:   [...live.attributes].map(a => a.name + '=' + a.value.slice(0, 40)) })
```

| Result | Generating source |
|---|---|
| Node present in server HTML, attributes identical | **Razor** — continue at Rung 2 |
| Node present, attribute differs / added / removed | a **script** changed it after load — Rung 4 (script) |
| Node absent from server HTML | **script-built** or **AJAX-inserted** — Rung 3 / Rung 4 |

For content that appeared after an interaction, find the request that delivered it (the network log, or
the script that issued it). An endpoint returning HTML is an action returning `PartialView(...)` (or a
Razor Page handler) — trace that partial with Rung 2.

## Rung 2 — Which Razor file rendered it?

1. **Route → action → view.** Map the URL with the conventional routes (`MapControllerRoute`,
   `RouteConfig`), `[Route]` attributes, and areas to a controller action. The view is the one it returns:
   `return View()` → `Views/<Controller>/<Action>.cshtml` (or `Areas/<Area>/Views/…`, then
   `Views/Shared/`); `return View("Name")` → that name. Razor Pages: the `Pages/` path matches the URL.
2. **Layout vs view.** Header, nav, footer, skip link and `<html lang dir>` come from the layout selected
   by `_ViewStart.cshtml` (per folder) or an explicit `Layout =`. A defect repeated on every page is almost
   always the layout or a partial it renders.
3. **Distinctive markers — grep the source for them**, in order of reliability:
   - a **distinctive class, `id` or `data-*` attribute** → grep `*.cshtml` (and `*.cs` for generators);
   - **`asp-for`/HTML Helper output**: `name="Address.City"` / `id="Address_City"` / `name="Items[0].Qty"`
     mean `asp-for="Address.City"` / `Html.TextBoxFor(m => m.Address.City)` / an indexed loop or
     EditorTemplate — grep the property name;
   - **`data-val-*`** attributes → a Tag Helper or HTML Helper on a model property with DataAnnotations;
     **`data-valmsg-for`** / `field-validation-*` → a validation message helper;
     `validation-summary-*` → the summary helper;
   - **visible text → via the resource key, not the text.** Grep the `.resx` files (or the project's
     localization store) for the rendered value to obtain the key, then grep views and `.cs` for the key.
     If the text is in no resource file, that is itself a finding: the string is hardcoded — grep the
     literal and expect it in a view, a helper, or a script.
4. **Partials and templates.** Once the view is known, check whether the node sits inside something it
   renders: `<partial name=…>`, `Html.Partial`/`RenderPartial`/`PartialAsync`, `EditorFor`/`DisplayFor`
   (→ `EditorTemplates/<Type>.cshtml`), `Component.InvokeAsync`/`<vc:…>` (→
   `Views/Shared/Components/<Name>/Default.cshtml` or the named view).

## Rung 3 — Generated by .NET code rather than written in a view

When the markup is not in any `.cshtml` as written:

- **Custom Tag Helper** — the element or attribute matches a `[HtmlTargetElement]`; the fix is in its
  `Process`/`ProcessAsync`.
- **Custom HTML Helper** — a `@Html.Something(...)` call whose extension method builds markup with
  `TagBuilder` or strings.
- **View Component** — class logic chooses the view and model; the markup is in its view, the values may
  come from the class.
- **Built-in helpers** generate `id`, `name`, `for`, `data-val-*` — you cannot change what they emit, only
  what you pass them (extra attributes, a label expression, `[Display]` metadata).

## Rung 4 — Generated by script or a third-party widget

- **Project scripts** — grep hand-written script sources (from the profile's `Script sources`, never
  `wwwroot/lib` or minified output) for the node's class/id/data-attribute used as a **selector**
  (`$('.js-menu')`, `querySelector('[data-toggle-panel]')`), for `createElement`, `.html(`, `.append(`,
  `innerHTML`, template literals containing the markup, and for `setAttribute`/`.attr(` on the offending
  attribute. If the scripts are compiled from TypeScript or bundled, fix the **source**.
- **AJAX-inserted content** — the partial that the endpoint returns (Rung 2) owns the markup; the script
  that inserts it owns focus, announcements and any post-insert initialization.
- **Third-party widget** — vendor class prefixes, markup that appears in no project file, a wrapper the
  library injects. The fix is the library's documented configuration **at the call site** (the script that
  initializes it, or the markup it enhances) — never the vendor file.

## Rung 5 — Decide *which* file to edit

| Situation | Fix goes |
|---|---|
| Node written directly in a view | **that view** |
| Node in the layout, or a partial the layout renders | **the layout / partial** — affects every page using that layout |
| Node inside a shared partial / EditorTemplate / View Component, value identical for all callers | **the shared partial / template / View Component view** |
| … value differs per caller | **the call sites**, through the partial's existing model/`ViewData`/VC arguments — or an additive optional one (see `idioms.md` §6) |
| Markup produced by a custom Tag Helper / HTML Helper | **the helper** — one fix for every usage |
| Attribute/state set or changed by project script | **the script**, in the function that changes the visual state |
| Node inserted by AJAX | markup → **the returned partial**; focus/announcement → **the inserting script** |
| Third-party widget internal DOM | **the call site / initialization**, via documented options — never the vendor file |
| Built-in helper output you cannot change | **what is passed to it** (attributes, `[Display]` metadata, label expression) |

## Rung 6 — Blast radius, before you edit anything

```
Grep 'partial name="_Name"|Html\.(Render)?Partial(Async)?\("_Name"'  --glob "**/*.cshtml" -c   # partial usages
Grep 'Component\.InvokeAsync\("Name"|<vc:name'                        --glob "**/*.cshtml" -c   # View Component usages
Grep '<custom-element|custom-attribute'                                --glob "**/*.cshtml" -c   # Tag Helper usages
Grep 'Html\.MyHelper\('                                                --glob "**/*.cshtml" -c   # HTML Helper usages
Grep 'Layout\s*=|_ViewStart'                                                                    # which views use which layout
```

State in the report: **usage count**, whether the value is **caller-invariant** or **caller-specific**, and
which other findings collapse into this one fix (a shared EditorTemplate, validation pattern, layout, or
widget script is often responsible for dozens of nodes across many routes).

## Pitfalls that waste the most time

- **Stale output.** Views may be compiled at build time (edits need a rebuild/restart the user performs);
  scripts may be served from a bundle or minified file (`BundleConfig`, `bundleconfig.json`,
  `<environment>` tag helpers choosing `.min.js`); the browser may cache static files. Confirm which file
  is actually served before concluding a fix failed.
- **Wrong layout.** Areas and folders can have their own `_ViewStart.cshtml`. Check which layout the page
  used before editing one.
- **The same markup in many views.** Grepping a class finds all copies; use the route → action → view
  mapping to pick the right one, and consider whether the copies should share a partial (a refactor —
  report it, do not do it).
- **Content that exists only in one state.** Server-side `@if` branches (errors, empty states, roles) and
  AJAX-loaded fragments exist only after the right request — reproduce that state before tracing.
- **Duplicate ids from loops and repeated partials** silently break every `for`/`aria-*` reference to
  them — check for that specifically.
- **The node you were given may not be the node to fix.** A `button-name` failure on an inner `<span>` is
  fixed on the enclosing control; a validation failure on an input is often fixed in the shared template or
  helper that renders every input. Fix the cause, not the reported line.
